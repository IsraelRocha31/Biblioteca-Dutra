1. ARQUITETURA
--------------------------------------------------------------------------------
O projeto utiliza um único repositório GitHub conectado a dois serviços:

  Vercel   -> executa frontend e TODO o backend/server
  Supabase -> fornece SOMENTE o PostgreSQL e recebe migrations

Estrutura:

  Biblioteca-Dutra/
  |-- frontend/
  |-- backend/
  |-- api/
  |-- supabase/
  |-- package.json
  `-- vercel.json

frontend/, backend/ e supabase/ ficam na raiz do mesmo repositório.


2. FLUXO DE REQUISIÇÃO
--------------------------------------------------------------------------------
  Navegador
      |
      v
  Frontend na Vercel
      |
      v
  /api -> Backend Node/Express na Vercel
      |
      v
  POSTGRES_URL
      |
      v
  PostgreSQL do Supabase

O frontend não acessa Supabase diretamente.


3. FRONTEND
--------------------------------------------------------------------------------
Tecnologias:
  - React 18
  - TypeScript
  - Vite
  - CSS modularizado por responsabilidade

Responsabilidades:
  - interface
  - estado
  - comportamento
  - acessibilidade
  - comunicação exclusiva com /api

A aparência deve continuar centralizada em frontend/src/styles/.


4. BACKEND / SERVIDOR
--------------------------------------------------------------------------------
Tecnologias:
  - Node.js 22+
  - Express
  - pg
  - @vercel/functions
  - JWT
  - bcryptjs
  - Multer em memória

Responsabilidades:
  - autenticação de administradores
  - regras de negócio
  - endpoints REST
  - upload/leitura de capas
  - acesso ao PostgreSQL

O backend é executado na Vercel. Supabase não executa nenhuma parte do servidor.


5. SUPABASE
--------------------------------------------------------------------------------
Supabase é usado somente para PostgreSQL.

A pasta na raiz é:

  supabase/
  |-- config.toml
  |-- migrations/
  `-- seed.sql

Na integração GitHub do Supabase:

  Working directory: .

Novas migrations podem ser aplicadas automaticamente a partir da branch de
produção.

Não são utilizados pela aplicação:
  - Supabase Auth
  - Supabase Storage
  - Supabase Edge Functions
  - acesso do frontend pela Data API


6. BANCO
--------------------------------------------------------------------------------
Migration inicial:

  supabase/migrations/20260901225459_initial_schema.sql

Tabelas atuais:
  - admins
  - livros

A tabela livros armazena a capa no próprio PostgreSQL:

  foto_capa       BYTEA
  foto_capa_mime  TEXT

Os bytes da imagem não são carregados nas listagens. A API fornece:

  GET /api/livros/:id/capa

As tabelas têm RLS habilitado e nenhuma policy pública. O backend acessa o
PostgreSQL diretamente com a credencial de servidor.


7. VARIÁVEIS DE AMBIENTE
--------------------------------------------------------------------------------
O arquivo .env da raiz é versionado e funciona como contrato central.

Ele declara as 12 chaves da integração Vercel + Supabase, sem valores no Git:

POSTGRES_URL
POSTGRES_PRISMA_URL
POSTGRES_URL_NON_POOLING
POSTGRES_USER
POSTGRES_HOST
POSTGRES_PASSWORD
POSTGRES_DATABASE
SUPABASE_PUBLISHABLE_KEY
SUPABASE_SECRET_KEY
SUPABASE_URL
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY
NEXT_PUBLIC_SUPABASE_URL

Os valores reais podem ser injetados pela Vercel. Não existe .env.local, .env.example
ou outro arquivo de ambiente: somente /.env é aceito pelo projeto.

Configuração versionada do administrador:

SUPER_ADMIN_NAME
SUPER_ADMIN_EMAIL
SUPER_ADMIN_PASSWORD

Nesta versão de testes, JWT_SECRET possui um valor versionado para o sistema funcionar
imediatamente. Em produção, ele deve ser sobrescrito por uma Environment Variable segura da Vercel.


8. SUPER ADMINISTRADOR
--------------------------------------------------------------------------------
Existe no banco uma conta marcada com managed_by_env = TRUE. O backend sincroniza
essa conta com o .env. Alterar nome, e-mail ou senha e fazer deploy atualiza o
mesmo registro no PostgreSQL.

Nesta versão de testes, SUPER_ADMIN_PASSWORD=admin123 fica no .env. Para trocar,
edite a variável e faça commit/push.

O backend converte `SUPER_ADMIN_PASSWORD` em bcrypt antes de gravar no PostgreSQL.

Sincronização manual opcional:

  npm run admin:sync


9. DESENVOLVIMENTO LOCAL
--------------------------------------------------------------------------------
Instalar:

  npm install

Usar o mesmo /.env central também no desenvolvimento local.
Não criar arquivos .env dentro de frontend/, backend/, api/ ou supabase/.

Executar:

  npm run dev

Frontend: http://localhost:5173
Backend:  http://localhost:3000/api
Health:   http://localhost:3000/api/health


10. MIGRATIONS
--------------------------------------------------------------------------------
Criar:

  npm run db:new -- nome_da_mudanca

Arquivos ficam em:

  supabase/migrations/

Não altere migration já aplicada em produção.


11. DEPLOY
--------------------------------------------------------------------------------
Um push no GitHub alimenta os dois serviços:

  Vercel:
    - instala workspaces frontend/backend
    - compila frontend
    - publica frontend/dist
    - executa api/index.js como entrada do Express

  Supabase:
    - lê ./supabase/
    - aplica migrations PostgreSQL novas

CONFIGURAÇÃO CENTRAL (.env)
==========================
O /.env da raiz é o único arquivo de ambiente e a fonte única de configuração de runtime. O backend usa backend/src/config/env.js. No frontend, frontend/vite.config.ts lê e valida a configuração pública durante o build e injeta um objeto já pronto em frontend/src/config/env.ts; o navegador não acessa import.meta.env diretamente. Portas, CORS, JWT, bcrypt, administrador padrão, identidade da aplicação, paginação, upload, cache e parâmetros do pool PostgreSQL são definidos no /.env.

A exceção é supabase/migrations/: o schema do banco é aplicado pela integração GitHub do Supabase e não precisa ler o .env. CSS também permanece responsável exclusivamente pelo visual.

Execute npm run env:check para verificar o contrato antes de enviar alterações.
